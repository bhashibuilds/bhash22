Architecture Thinking

How I approach system design and infrastructure problems.

Scalability First

I design systems assuming they'll 10x in load tomorrow. This means horizontal scaling, stateless services, and distributed architectures. Key principles: no single points of failure, asynchronous over synchronous, and caching at every layer.

Example: Using Kafka + Flink for event streams instead of direct DB writes ensures the pipeline survives traffic spikes and allows backpressure handling.

Observability Built-In

You can't manage what you can't measure. Every service gets structured logging, distributed tracing, and metrics from day one. This isn't an afterthought—it's baked into the architecture.

Example: OpenTelemetry instrumentation across all services feeds into Prometheus + Grafana. Alerts trigger before users notice issues.

Cost as a Constraint

Cloud resources cost money. I design with cost efficiency in mind: spot instances for batch jobs, reserved capacity for base load, and automated shutdown for idle resources. Cheap architecture that doesn't run is not cheap.

Example: Karpenter + spot instances reduced our EKS bill by 40% while maintaining SLOs.

Infrastructure as Code

Terraform/Pulumi over clicking consoles. Every resource is versioned, reviewed, and reproducible. IaC is how we prevent config drift and enable fast, safe deployments.

Example: Terraform modules let us spin up prod-like environments in minutes, enabling faster testing and disaster recovery.

Data Consistency Tradeoffs

Not all data needs to be perfectly consistent. I think about CAP theorem, eventual consistency patterns, and when idempotency saves you. Trade latency for throughput where appropriate.

Example: Using event sourcing for the event stream lets us replay history and rebuild state, while materialized views serve eventual consistency to the API layer.

Fail Fast, Learn Faster

Design systems that fail visibly and loudly. Circuit breakers, timeouts, and bulkheads prevent cascading failures. Chaos engineering catches the surprises you didn't anticipate.

Example: Service timeouts at 2s prevent one slow dependency from bringing down the entire platform.

The bible for any data engineer. Deep dives into distributed systems concepts—consistency models, replication, partitioning, transactions. I reference this constantly. The chapters on stream processing and consensus algorithms are pure gold.

Site Reliability Engineering

Google

How Google runs production systems at scale. Changed my perspective on error budgets, on-call culture, and postmortems. The SLI/SLO framework is invaluable. If you care about reliability, read this.

The Art of Computer Systems Performance Analysis

Statistical rigor for performance work. Most perf analysis is hand-wavy; this book teaches you how to actually measure and reason about systems. Dense but worth it.

A classic on software project management. Written in 1975 but still relevant—Brooks' Law ("adding people to a late project makes it later") still holds. Great perspective on system design and team dynamics.
